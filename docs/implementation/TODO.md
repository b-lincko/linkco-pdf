- Status: **complete**; parent(s): REC-B07.

- Audit: Started from the recommendation's done-when — concurrency, input and output quotas and timeouts that can be configured and audited — and asked what each part could mean in a program that is mostly one file in, one file out. ### B028: A caller can tell what it is talking to, and what went wrong

- Status: **complete**; parent(s): REC-B02.
- Acceptance: The tool table carries one version, printed with the whole table by `pdfcraft-cli schema` and reported identically by the MCP server in `initialize` and `tools/list`; a caller can ask whether the build speaks the revision it was written against and gets an answer it can act on (exit 3 when the major version differs) rather than discovering the mismatch mid-job; the rule for bumping the version is written down and the major number is held by a test; every failure the tools can raise carries one stable kind from the same vocabulary the command line uses for its exit codes, and the MCP server returns that kind as a value (`structuredContent.error.kind`) so a client branches on it instead of parsing the message.
- Audit: Started from the two halves B015 left open and asked what a version has to be worth. The first decision was that the version is a property of the table, not of a tool or a call: a per-tool version would multiply the things to keep in step, and the unit a caller depends on is the set of tools it can call. The second was that the number must be reported in every place a caller can look — the CLI, `initialize`, `tools/list` — from one constant, so the three cannot disagree; `tools/list` carries it in `_meta` rather than inventing a field on the protocol's own `tools` array. The third was the bump rule: a version with no stated rule is decoration. The module documents two lists (additive changes bump the minor; removing or renaming a tool, making an optional argument required, removing or changing a documented result field, or changing what a tool does to a document bumps the major), and a test holds the major at 1 so that a bump is a decision someone makes rather than a typo. Because the document is built from `tools()` at call time, the count it prints cannot drift from the tools that exist — the audit of B026 had already found one listing path that drifted from the table, so this time the description reads the table itself. Fourth, the compatibility answer: `--schema-version V` compares majors only, because that is exactly what the version promises; a minor difference is compatible in both directions and the document is printed either way so the caller can see which minor it actually got. The failure taxonomy came next, and the audit of it changed the design twice. ### B046: A save survives a power loss: the folder holding the new name is flushed after the rename (REC-R01)

- Status: **complete**; parent(s): REC-R01.
- Acceptance: A save that returns success is the file that is still there after the machine loses power, not only after the writing process crashes. `pdfcraft_platform::staging::sync_dir` flushes the folder itself (on Unix, opening it and flushing the descriptor through the same `sync_staged` rule the files use, including the macOS FUSEFS plain-fsync fallback; on non-Unix it is a documented no-op that reports success). Every save path flushes the folder after a successful rename: `replace_file` (the command line and every other caller of it), the automation writer `write_atomic_using` and the desktop save `write_atomically_using`. A folder that cannot be flushed fails the save rather than reporting success, and on the automation path that is a normal tool failure. Tests: `sync_dir` succeeds on a real folder and reports a missing one; the process-kill boundary test in both the automation and the desktop suite gains a `synced` phase that pauses after the save has returned, so a kill at that boundary is shown to leave the complete new file, no staging file, and a retry that succeeds.
- Audit: REC-R01's open note: power-loss durability. The audit of what existed: B001-B007 built write → flush → close → rename, so the bytes are on the disk before the target name changes, and a reader or a killed process sees the old file whole or the new file whole. What none of them flushed is the directory entry: on Unix a rename is durable only once the folder that contains the name is itself flushed, so after a power cut the volume can come back with the old name pointing at the old file even though the new file's bytes were flushed — the save reported success and the work is gone. Decisions. (1) One new operation, `sync_dir`, rather than a flush call pasted into three crates: the folder open, the macOS fallback and the platform difference live in one place beside the flush rule they share. (2) It is called on the success path after the rename, never before: a folder flushed before the rename says nothing about the new name. (3) On non-Unix it reports success without doing anything, because the standard library has no folder flush there — Windows documents a rename as flushed with the file's own flush, and the handle a real folder flush needs is not one this crate opens; the doc comment says so rather than pretending. (4) It runs in production save paths only; the test seams in the two writers are unchanged, so a test can still inject write, flush and rename failures. (5) A flush that fails fails the save: a save that cannot be made durable is reported as not durable, and the tool's caller sees the error instead of a false claim of success. Not claimed: a physical power-cut test (no harness can do that here), meta-data durability of the staging file's own directory entry before the rename, the app's control-file write in apps/pdfcraft/src/main.rs (it is not a document save and is outside this component), or the rest of REC-R01.
- Ci: passed
- Notes: Closes REC-R01's power-loss durability note for document saves: after a save that returned success, the new file's name and bytes are both flushed to the volume, so a power loss cannot resurrect the old file. Still open in REC-R01: physical volume-full, whole-application restart and session recovery, and the full save-integrity release gate, which needs a signed build and machine-level testing. This is a durability step, not a re-do of the atomic-save guarantee B001-B007 established.

### B047: Regenerate field appearances: a value without an appearance becomes visible (REC-F01)

- Status: **complete**; parent(s): REC-F01.
- Acceptance: The tool `form_regenerate_appearances` (and the engine call under it, `pdfcraft_forms::regenerate`) redraws the normal appearance of every widget whose `/AP` is missing or no longer matches what the field would draw now, from the field's value, `/DA` font/size/colour, quadding, `/MK` background and border colours, and `/MK /R` rotation — the same drawing a fill makes, using the existing `field_appearance`. Only a widget that is missing an appearance or whose stored appearance differs from what would be drawn is redrawn, so a second run draws nothing and changes no bytes; an appearance that already matches is kept untouched. Push buttons (icons) and signature fields (marks) are reported as unsupported and left alone, because their appearance is not the field's value drawn from `/DA`. `fields` limits the work to the named fields (all when absent), and a name that is not a field is refused. The answer says what was found: `drawn` (missing + stale), `missing`, `stale` and `unsupported` lists. The change is one undo step (labelled Regenerate field appearances), adds no bytes when nothing is missing or stale, and is in the tool catalogue with a schema and a stated reason in examples.rs.
- Audit: REC-F01's open notes: form.appearance-regeneration (partial) and form.push-buttons (partial). The audit of what existed: `pdfcraft_forms::appearance` already draws text and choice fields correctly — single-line, multiline, comb, password, quadding, auto size, combo/list selection, `/MK` background and border, `/MK /R` rotation, and the approximate Helvetica metrics — and `redraw` applies it, but only as a side effect of `set_value`/`reset`/`recalculate`. Nothing could redraw a field that already had its value. So a form produced by another tool that writes `/V` without an `/AP` (permitted by the specification, which says a viewer may regenerate) showed nothing in the value area, and PdfCraft could not fix it either: the value was in `form_fields`, the page showed an empty box, and re-filling with the same value was the only workaround — which fails for a field the caller cannot re-derive. Decisions. (1) The unit of work is the appearance, not the value: the existing drawing is reused verbatim, so the tool cannot drift from what a fill draws. (2) Only missing or stale appearances are redrawn, compared as decoded content streams: a widget whose appearance already matches is left byte-for-byte alone, so running the tool over a correct form is a no-op that does not bloat an incremental save, and an appearance a producer made more carefully than this code can survive. (3) A stored stream that cannot be decoded counts as stale and is redrawn rather than trusted. (4) Buttons and signatures are reported `unsupported` rather than given an invented appearance — a push button's icon comes from `/MK /CA` or an image and a signature's mark from a real signature, neither of which this code draws from a value. (5) The reporting comes from a preview (`Session::preview_field_appearances`) run on a clone of the editor's live state before the edit, so the answer describes unsaved edits too, and the edit itself is the ordinary undoable one. (6) The tool is not destructive: it replaces appearances it has established do not match, and never removes content. Not claimed: form.push-buttons (running a button's actions on click) is still open, and this does not regenerate `/D` or `/R` appearances, appearance streams a producer made with a font this code cannot measure, or XFA-drawn fields.

Still open in REC-F01: push buttons running their actions, and the required-field validation and completion guide the recommendation also names. The combination is not a form-validation model.
